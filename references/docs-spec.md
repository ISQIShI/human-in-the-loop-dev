# 文档规范

文档的作用是让用户在任何时候都能用几分钟看懂项目现状。它们是协作循环的产物，不是事后补写的说明。

下文的路径都是项目内的路径；模板在本技能的 `assets/docs/` 中。

## 文档一览

| 文档 | 回答的问题 | 何时更新 |
|---|---|---|
| `docs/architecture.md` | 项目现在由哪些模块组成，它们如何关联 | 每个实现步骤完成并经用户确认后 |
| `docs/roadmap.md` | 现在做到哪一步，接下来做什么 | 切片时，以及每个步骤完成后 |
| `docs/decisions/` | 为什么这样设计 | 每次讨论得出结论后 |

## 通用规则

- **只记录已确认的内容**：文档写入或修改前必须经用户确认。讨论中的想法不进文档。
- **保持简短**：`architecture.md` 和 `roadmap.md` 各自不超过约 100 行；一条决策记录不超过约 40 行。
  超出时先精简，仍然超出再考虑拆分。
- **一个事实只写在一处**：其他地方用链接引用，不复制内容。
- **描述现状**：`architecture.md` 和 `roadmap.md` 只反映当前状态，历史由决策记录和 git 提交承担。
- **与代码同步**：文档更新和对应的代码改动放在同一次提交里。
- **语言与命名**：正文用中文；文件名用小写英文和连字符，例如 `market-data-storage.md`。
- **不新增文档类型**：需要新的文档类型时，先作为一个决策讨论。
- **引用本技能时不写文件路径**：项目文档提到本技能的内容时，写“使用 `human-in-the-loop-dev` 技能，
  见技能内的某个文件”，不写技能在项目中的安装路径，因为不同 AI 工具的技能目录不同。

## 模块地图：architecture.md

每个模块一个条目，包含四项：

- **职责**：一两句话说明这个模块做什么、不做什么。
- **位置**：代码所在的路径。
- **依赖**：它依赖哪些模块，被哪些模块依赖。
- **相关决策**：指向对应决策记录的链接。

文件开头放一张模块依赖关系图（Mermaid），模块增减或依赖变化时同步修改。
不写实现细节，实现细节以代码为准。

## 路线图：roadmap.md

分三节：

- **当前步骤**：同一时间只有一个。
- **接下来**：已切片、按顺序排列的步骤，一般不超过 5 个，更远的计划不写。
- **已完成**：最近完成的步骤，附提交哈希；超过 10 条时删去最旧的。

每个步骤写成一行：做什么，以及做完的标志。步骤大小遵循本技能 `SKILL.md` 中“步骤要小”的规定。

## 决策记录：decisions/

- 一条记录只写一个决策，文件名为 `NNNN-简短标题.md`，编号从 `0001` 起递增，不复用。
- 新建时复制项目中的 `docs/decisions/0000-template.md`。
- 状态取以下之一：`已采纳`、`已废弃`、`被 NNNN 取代`。
- 记录一经采纳，正文不再修改。决策变化时新建一条记录，并把旧记录的状态改为 `被 NNNN 取代`。
- 需要记录的决策：架构、技术选型、模块边界、数据结构、对外接口，以及其他日后会被问到“为什么”的选择。
  纯实现细节不需要记录。
